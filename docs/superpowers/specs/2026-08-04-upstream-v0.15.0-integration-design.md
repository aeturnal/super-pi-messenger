# Upstream v0.15.0 Integration Design

## Purpose

Integrate the complete `nicobailon/pi-messenger` v0.15.0 release into Super Pi Messenger while retaining the fork's identity, independent Superpowers boundary, and intentional product behavior.

The integration starts from Super Pi Messenger `main` at `3315090` and uses upstream tag `v0.15.0` at `2f5e7dc`. It covers all eight upstream commits after the shared base:

1. `2c3b748` — optional Crew Team layer
2. `8d24757` — Team workflows for current Pi
3. `5cb1f53` — backlog compatibility fixes
4. `817e1ae` — legacy installer package-conflict guard
5. `bd76c63` — Crew session-model inheritance
6. `a97fbf2` — compact Crew event artifacts
7. `2e83f14` — bounded feed reads and reused task snapshots
8. `2f5e7dc` — v0.15.0 release metadata

## Integration Structure

Perform the work in the isolated worktree `.worktrees/upstream-v0.15.0-integration` on branch `integrate/upstream-v0.15.0`. The branch starts from current Super Pi Messenger `main`, not from an unmerged feature or documentation branch.

Cherry-pick all eight upstream commits in their original order. This preserves authorship, attribution, and logical history. Small follow-up commits may adapt imported behavior to the fork when keeping that adaptation separate makes review clearer.

The upstream remote remains fetch-only with its push URL disabled. The integration must not add automatic synchronization or make Super Pi Messenger `main` track `upstream/main`.

## Conflict Policy

Resolve purely mechanical conflicts directly. Mechanical conflicts include imports, formatting, path movement, and test adjustments that do not change product behavior.

Retain Super Pi Messenger identity in branding and metadata conflicts. This includes the package name, repository links, product description, independent-maintenance statement, and independent Superpowers installation boundary.

Pause for user review whenever a conflict changes meaningful behavior. For each such conflict, present:

1. the upstream behavior;
2. the existing fork behavior;
3. the practical effects of each choice; and
4. a recommended resolution.

Record the user's decision and the final resolution in the integration report. In particular, Team and Crew workflow changes must not silently override Super Pi Messenger's Superpowers authorization design.

## Integration Checkpoints

### Checkpoint A: Team foundation

Import `2c3b748` and `8d24757`.

Validate Team storage, routing, approvals, task execution, overlays, and existing Crew behavior. Treat clashes with the fork's Superpowers integration and automatic Crew authorization as meaningful behavior conflicts.

### Checkpoint B: Compatibility

Import `5cb1f53` and `817e1ae`.

Adopt the Pi, TypeBox, and installer safeguards while retaining the fork's package identity and installation contract.

### Checkpoint C: Runtime improvements

Import `bd76c63`, `a97fbf2`, and `2e83f14`.

Validate session-model inheritance, artifact compaction, feed tail bounds, task snapshot reuse, overlays, and affected fork behavior.

### Checkpoint D: Release reconciliation

Import `2f5e7dc` and reconcile its release metadata. Record compatibility with upstream v0.15.0 without restoring the upstream package identity or making an unapproved fork release. The fork's final version remains a separate release decision.

## Validation

At each checkpoint:

1. inspect the resulting production and test changes;
2. run TypeScript diagnostics on changed files;
3. run focused tests for the imported behavior;
4. run the complete Vitest suite; and
5. stop at the first unexplained failure.

Before completion, run `npx tsc --noEmit` and the complete test suite from fresh command output. Compare the finished branch with the upstream commit range and account for every upstream production change as retained, adapted, or explicitly incompatible.

Upstream tests should remain unless a documented fork-specific replacement covers the same behavior. Existing fork tests must continue to pass.

## Integration Record

Create an integration report that records:

- upstream repository, tag, and commit range;
- integration branch and fork base;
- conflicts and user decisions;
- fork-specific adaptations;
- retained or replaced upstream tests;
- diagnostic, type-check, and test results;
- remaining risks;
- authorship and attribution; and
- final review decision.

## Completion Criteria

The integration is ready for review only when:

- all eight upstream commits are represented in branch history;
- every upstream production change is retained, adapted, or explicitly documented as incompatible;
- upstream and fork tests are retained or replaced with documented equivalent coverage;
- TypeScript checking and the complete Vitest suite pass;
- Super Pi Messenger branding, package identity, repository links, and independent Superpowers boundary remain intact;
- no automatic upstream synchronization or tracking is introduced; and
- the integration report is complete.

The completed branch will be presented for review. It must not be merged into `main`, pushed, published, or released without explicit user approval.
